# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ElasticMigrate (`esmigrate` CLI, package name `elastic-migrate`) is a Flyway-style schema migration tool for Elasticsearch. It applies versioned schema script files against an ES cluster and records the applied versions and every run in SQL tables (via SQLAlchemy). v2.0.0 modernized the tool for Python 3.11+ and Elasticsearch 8 and is released; v3.0.0 (golang-migrate style up/down migrations) is in progress on `main` — see "Current state" below before changing tooling or dependencies.

## Working rules

- **Minimal comments in source code.** The code is simple; tests do the explaining. Add a comment only when something is genuinely non-obvious. Explanations, design notes and user guides belong in `docs/`.
- **Maximum test coverage.** This module is used in enterprise, government-level applications. Every change ships with tests covering all new/changed branches, including error paths and exit codes; never lower coverage.
- **Plan before large changes.** For anything beyond a small fix, first write a plan and create/update the GitHub issue(s); implement only after that.
- **Small commits.** Split an issue's tasks into several small commits in a sensible order, each with its own tests, instead of one large implementation commit followed by the tests. The branch must be green before its PR.
- **Commits:** author `Zobayer Hasan <zobayer1@gmail.com>`. Commits made by Claude end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` and nothing else (no `Claude-Session` links); when the user commits a drafted message themselves, the trailer is optional. No trailer or AI attribution in issue/PR bodies or comments. Show the proposed commit message to the user and wait for approval before committing.
- **Commit messages:** a short imperative subject and a short body saying what changed and why. Do not repeat requirements that are already written in the issue; reference it instead, with `Closes #N` on the commit that completes the issue and `Refs #N` on the others.

## Commands

```bash
uv sync                                               # create/update .venv (Python 3.11 from .python-version) with dev group
uv run pre-commit install                             # (re)install git hook after .venv is recreated
uv run pytest --cov                                   # full suite, branch coverage, fails under the fail_under floor
uv run --isolated --python 3.14 pytest --cov          # same on 3.14 without touching .venv
uv run pytest tests/test_internals/test_script_parser.py   # single file
uv run pytest tests/test_cli/test_upgrade.py::test_cli_upgrade_cmd_fails_with_value_error   # single test
uv run ruff check --fix .                             # lint (incl. import sorting, pyupgrade)
uv run ruff format .                                  # format
uv run pyright                                        # type check: strict for esmigrate/, standard for tests/
uv run pre-commit run --all-files                     # ruff check/format, whitespace/EOF fixers, pyright
docker compose up -d --wait                           # ES 8.19 (plain :9200, HTTPS+auth :9201, mTLS :9202), PostgreSQL 17, MySQL 8.4
uv run pytest -m integration                          # integration tests (all three DBs + real ES), no coverage floor
docker compose down                                   # stop services (data is ephemeral)
uv run --group docs sphinx-build -W --keep-going -b html -d docs/_build/doctrees docs docs/_build/html   # docs
uv build                                              # wheel + sdist
uv lock --upgrade                                     # manual dependency update (no bots)
```

- `uv run pytest` excludes integration tests (`addopts = -m "not integration"`). Integration tests fail, never skip, when a service is down. Ports can be moved with `ESMIGRATE_ES_PORT` / `ESMIGRATE_PG_PORT` / `ESMIGRATE_MYSQL_PORT`; tests read `ESMIGRATE_TEST_ES_URL` / `ESMIGRATE_TEST_PG_URL` / `ESMIGRATE_TEST_MYSQL_URL` (plus `ESMIGRATE_TEST_MYSQL_ROOT_URL`, used only to create per-test MySQL databases for `schema_db_schema` tests; PostgreSQL schemas are created by the `esmigrate` owner). Compose credentials (`esmigrate`/`esmigrate`, ES `elastic`/`esmigrate-secret`) are local test-only values. The one-shot `es-certs` service writes a test CA, server and client certificate to the git-ignored `.certs/` (reused across runs; delete it to regenerate). Secured clusters move with `ESMIGRATE_ES_SECURE_PORT` / `ESMIGRATE_ES_MTLS_PORT`; tests read `ESMIGRATE_TEST_ES_SECURE_URL` / `ESMIGRATE_TEST_ES_MTLS_URL` / `ESMIGRATE_TEST_ES_PASSWORD` / `ESMIGRATE_TEST_CERTS_DIR`.
- All config lives in `pyproject.toml`: build (hatchling + hatch-vcs), ruff, pytest (`DeprecationWarning`/`PendingDeprecationWarning` are errors), coverage (`fail_under` is a floor — raise it, never lower it). Only pass `--cov` for full runs, otherwise single-test runs trip the coverage floor.
- Version comes from git tags via hatch-vcs and is read at runtime with `importlib.metadata`, so the package must be installed (`uv sync` does this).

## CI

- `.github/workflows/ci.yml` runs on every push, PRs to `main` and manually: `lint` (pre-commit incl. strict pyright), `unit` and `integration` (Python 3.11 and 3.14; integration starts the full `docker compose` stack), `build` (`uv build` + `twine check --strict`). Jobs call the same `uv run …` commands used locally.
- `ci.yml` also has a `docs` job building the Sphinx site with warnings as errors. `.github/workflows/pages.yml` builds and deploys the docs to GitHub Pages (`https://zobayer.net/elastic-migrate/`, inherited from the `zobayer1.github.io` custom domain — never add a `CNAME` file or `sphinx.ext.githubpages`) on pushes to `main` and manual runs only. The `github-pages` environment accepts deployments from `main` alone, so the workflow has no `release` trigger (a release event runs on the tag and is rejected); `sign-release.sh` starts it on `main` after publishing.
- `.github/workflows/release.yml` runs on `v*` tags (`vX.Y.Z` with optional `a`/`b`/`rc` suffix): tests, reproducible `uv build` (`--build-constraints build-constraints.txt --require-hashes`, `SOURCE_DATE_EPOCH` = commit time, uv version and uv-managed CPython pinned in `build-toolchain.env` — system Pythons linked against zlib-ng, as on Fedora, compress archives into different bytes), `SHA256SUMS`, build provenance attestations and a **draft** GitHub release. `scripts/sign-release.sh [--dry-run] TAG` (run locally by the maintainer) checks draft state, the tag's GPG signature against trusted fingerprints, checksums, attestations and a byte-identical local rebuild (`uvx uv@$UV_VERSION`, pinned CPython installed into a temporary directory), then signs with subkey `A76F…C188`, uploads `.asc` files and publishes. Signing never happens in CI; releases go to GitHub only (no PyPI). Shell scripts are checked by the shellcheck pre-commit hook.
- Coverage goes to Codecov via **OIDC** (`use_oidc: true`, `id-token: write`) — no token secret; flags `unit` / `integration`.
- Action versions: use the newest major releases and check `runs.using` is `node24` (no deprecated Node runtimes). Actions that receive a write token, a secret or an OIDC token are pinned to a commit SHA with a `# vX.Y.Z` comment; others use major tags where the publisher maintains them (`astral-sh/setup-uv` publishes no major tags, so it is SHA-pinned too — check `gh api repos/<owner>/<repo>/git/ref/tags/vN` before using a major tag). Validate workflow edits with `uvx --from actionlint-py actionlint`.

## Architecture

Flow of `esmigrate -p <profile> upgrade` (all orchestration lives in the `esmigrate/cli` package: `main.py` has the command group and registers the commands, `upgrade.py` the `upgrade` command, `execution.py` the script parsing and execution, `common.py` the profile loading, error mapping, database connection and lock helpers they share; the other commands are still in `main.py` until #284 moves them):

1. **`contexts.ContextConfig`** — `main()` only records the profile name and log options in `ctx.meta`; each command loads the profile when it runs via the `@pass_config` decorator (`load_config`), so `esmigrate <command> --help` works without any configuration (#271). Config files are read in order: user config dir (`platformdirs`), `./config.json`, then `$ESMIGRATE_CONFIG`; later files overwrite earlier ones. Profile fields: `elastic_host` (http/https URL, any host incl. single-label names, no embedded credentials), `elastic_headers`, `elastic_timeout` (default 60s, `null` disables), `elastic_username`/`elastic_password` or `elastic_api_key`, `elastic_ca_certs`, `elastic_verify_certs` (default true; false prints a warning every run), `elastic_client_cert`/`elastic_client_key`/`elastic_client_key_password` (mTLS), `schema_db`, `lock_timeout` (seconds, default 0), `schema_db_schema` (PostgreSQL schema / MySQL database for the esm tables; rejected for SQLite; psycopg2 `?options=` URL parameters are rejected in favour of it), `schema_dir` (**required**, no fallback to the working directory), `schema_ext` (default `.esm`; v1 default was `.exm`), `schema_namespace` (default `default`). Missing or invalid values raise `InvalidConfigurationError` (exit 11) at profile load. Filename regex comes from `$SCHEMA_PATTERN`, compiled in `ContextConfig.__init__` and matched with `fullmatch`: named groups `version`, `sequence`, `name`, `extension` are required, `direction` (`up`/`down`) is optional, and an invalid regex or a missing group is `InvalidConfigurationError` (exit 11). Profiles from all config files are merged per field, then every string value (also nested in headers/lists) has `${VAR}` references resolved from the environment — an unset variable is an error. `esmigrate config` masks passwords, API keys and `Authorization` headers. Default profile is `default` (`commons.DEFAULT_PROFILE`; was `test` in v1, #108).
2. **`internals.GlobLoader.load_migrations`** (sync, local disk) — `scan_dir` globs `schema_dir` for `*<schema_ext>`, validates names (`V1_10__name.up.esm` → `commons.MigVersion(1, 10)`, direction `up`; without a `.up`/`.down` segment it is a plain file) and returns one `commons.ScriptData` per file sorted by version then path, with `path` relative to `schema_dir`. `internals.pair_scripts` groups them into `commons.Migration`s (`up` is the `.up` or plain file, `down` the `.down` file). A version is a plain file alone, an `.up`, a `.down`, or an `.up` and `.down` with the same name; bad file names and bad sets are each listed in one aggregated error (exit 31) before any request. `upgrade` only runs `up`; a `.down`-only migration is recorded without requests, with `script` and `checksum` empty.
3. **`internals.ScriptParser.get_commands`** — Kibana-console-like script → `commons.Command`s: a `VERB path` line (GET/PUT/POST/DELETE) plus optional JSON/NDJSON body. Emits host-relative paths (`/twitter/_doc`); absolute and protocol-relative URLs are rejected. `cli.execution.parse_scripts` parses every pending script before the first request and lists all failures in one `InvalidCommandScriptError` (exit 32), with nothing sent or recorded.
4. **`internals.HTTPHandler`** — `async with HTTPHandler(ctx)` wraps one `httpx.AsyncClient` (base URL = `elastic_host`, profile headers, timeout). Non-2xx → `ElasticsearchHTTPError` (carries `.response`); transport errors/timeouts → `ElasticsearchConnError`, whose `never_reached` is true only for `httpx.ConnectError`, `httpx.ConnectTimeout` and TLS certificate alerts (`request_never_reached`). Plain HTTP by design — no elasticsearch-py client.
5. **`internals.DBManager`** — `async with DBManager.connect(url, namespace=..., upgrade=False, schema=...)` detects the table layout (`detect_layout`; the v1/v2 detection and row copy live in `internals.legacy_layout`), refuses a v1/v2 layout with `LegacySchemaTableError` (exit 22) unless `upgrade` (`init`), creates missing tables (`create_all`; a failure is exit 20 with an `init --print-sql` hint), checks the columns of both tables (`InvalidSchemaTableError`, exit 22), copies v1/v2 rows when upgrading (`copy_old_rows`), and always disposes the async engine. `internals.db_engine` creates the engines, the table SQL and the schema/column checks: bare URLs are mapped to async drivers (`sqlite`→aiosqlite, `postgresql`/`postgres`→asyncpg, `mysql`/`mariadb`→asyncmy); sync drivers are rejected; engines use `hide_parameters=True`, so database errors never carry request or response bodies; `create_tables_sql(url, schema)` renders the DDL without connecting. Runs are recorded with `start_run` (returns a `ScriptRun`; the rows come from `migration_to_state` and `migration_to_history`), `finish_run` and `undo_run`, each committing both tables in one transaction. Every query is scoped to the namespace. `schema=` applies `schema_translate_map` to the engine, and raw SQL / inspection pass the schema explicitly (`qualified_name`); a missing schema is an `InvalidDBConnectionError`.
6. **`models.SchemaState`** — table `esm_schema_state`, one row per applied version, PK `(namespace, version_base, version_rank)` with a read-only `.version` property returning `MigVersion`, `installed_rank` unique per namespace, `success` true/false/NULL (NULL = running or interrupted), `execution_time` in milliseconds, `installed_on` UTC via `models.types.UTCDateTime`. **`models.SchemaHistory`** — append-only table `esm_schema_history`: autoincrement `id` (event order), `operation` (`commons.Operation`: up/down/force/reset), nullable version, index `(namespace, id)`. Portable across SQLite/PostgreSQL/MySQL; dialect differences use `with_variant`, never separate model classes.

Key behaviors:
- **Async boundary:** click commands are sync and call `sys.exit(asyncio.run(run_<command>(cfg)))`; async functions return exit codes instead of calling `sys.exit`, so `async with` cleanup always runs. Scripts and commands execute strictly sequentially.
- **Run recording:** a script's start is committed before its first request (state row `success = NULL`, inserted for up and updated for down, plus a history row). Afterwards `finish_run` stores the result (up: `true`/`false` with duration and requests; down: deletes the row on success, `false` on failure), or `undo_run` reverts the start when the first request never reached ES (exit 51) and the history keeps a failed row. A failed or interrupted latest row makes `upgrade` exit 21 (pointing to `status`/`force`) and blocks every later start; a down can only start on the latest row. Until #278/#279, `rollback` deletes failed rows (not interrupted ones) and `reset` deletes all state rows; no command deletes history rows. `upgrade` warns about unapplied migrations below the latest applied version and never applies them.
- **Migration lock:** `upgrade`, `rollback` and `reset` hold a lock per (schema database, schema, namespace) for the whole run via `DBManager.lock()` (`internals.migration_lock`): PostgreSQL advisory locks and MySQL `GET_LOCK` on a dedicated autocommit connection (released automatically if the process dies), a lock row in `esm_schema_lock` on SQLite (stale holders on the same host with a dead pid are taken over; never on Windows, where `os.kill(pid, 0)` would send CTRL_C). `lock_timeout` (default 0) controls waiting; a held lock is `MigrationLockedError` (exit 23) naming the holder. `esmigrate unlock` removes a stuck SQLite lock after confirmation. `init` is not locked.
- **Old layouts:** v1 and v2 stored versions in `esm_schema_version`. With rows in it (and none in `esm_schema_history`), every command except `init` exits 22; `init` copies the rows into the new tables with INSERTs only, in one transaction (v1: `default` namespace, file names, local time → UTC; v2 naive times are already UTC; `execution_time` × 1000; unusable or colliding versions exit 21 with nothing written) and never alters or drops `esm_schema_version`, which stays as the backup. Accounts without DDL rights work when a DBA creates the tables from `esmigrate init --print-sql`. No silent schema changes.
- Failure categories map to positive exit codes in the `exceptions.Errors` `IntEnum`, grouped by tens (1x profile/config, 2x DB, 3x schema files, 4x params, 5x HTTP); never use 1, 2, 126–127 or 128+ (uncaught error, click usage error, shell, signals). The shell sees exactly these values. The CLI prints `<ExceptionName>: <message>` via `cli.common.fail()`.
- **Logging:** everything logs under `esmigrate` (`logging.getLogger(__name__)`); only the CLI configures handlers (`commons.log_setup`). Console handler on **stderr** (INFO default, `-v` DEBUG, `-q` warnings/errors); **stdout** is reserved for real output (`config`, `init --print-sql`, `--version`, banner). Optional log file (`log_file` profile field or `--log-file`, always DEBUG, UTC timestamps) with `log_rotation: size` (`RotatingFileHandler`, `log_max_bytes` 10 MiB, `log_backup_count` 5) or `external` (`WatchedFileHandler` for logrotate). The audit trail records run start (version, command, profile, namespace, host, masked DB URL, OS user, machine), each script (file, checksum, result, duration), each request (verb, path, sizes, status, duration) and the exit code. Never log credentials, `Authorization` headers or request/response bodies; DB URLs go through `mask_db_url`. `DBManager` does not log state changes (logging in internal modules is undecided). `tests/conftest.py` closes esmigrate log handlers after every test.
- Nothing stores the ES host: request paths in `query_results` are host-relative and `script` is relative to `schema_dir`.

## Coding style

- Python 3.11+ idioms, enforced by ruff (`E W F I UP B SIM C4 PT RUF ANN2 TID252`, line length 120): no encoding headers, no `(object)` bases, `X | None`, builtin generics, `typing.Self`, `collections.abc` types, `raise ... from err` inside `except`.
- Return type hints are required on all functions in `esmigrate/` (`ANN2`); tests are exempt.
- pyright must report 0 errors: **strict** mode for `esmigrate/` (no unknown types — annotate empty collections, use `dict[str, str]`/`tuple[...]` not bare generics, `cast` JSON values after `isinstance`), standard mode for `tests/`. Narrow optionals with `assert x is not None` / `isinstance` in tests; use `STATE_TABLE` / `HISTORY_TABLE` (typed `Table`) instead of `SchemaState.__table__` / `SchemaHistory.__table__`. Use `-> AsyncGenerator[T, None]` (not `AsyncIterator`) for `@asynccontextmanager`.
- Private attributes use a leading underscore (`self._ctx`); short-lived locals and loop vars are often underscore-prefixed (`_path`, `_ver`, `_file`). f-strings throughout.
- Imports are always absolute and fully qualified (`from esmigrate.commons.command import Command`), never relative (`from .command import ...`); ruff `TID252` enforces this.
- Subpackages re-export their public API through `__init__.py` with an explicit `__all__`. Other packages import from the package (`from esmigrate.internals import ScriptParser`), not the submodule; modules inside a package import their siblings by submodule path (`from esmigrate.commons.mig_version import MigVersion`), because importing from their own package's `__init__` is circular.
- Custom exceptions live in `esmigrate/exceptions/__init__.py`: subclass `RuntimeError`, one-line docstring `"""Raised when ..."""` plus `pass` (or a small `__init__` when they carry data, like `ElasticsearchHTTPError.response`), kept alphabetical and listed in `__all__`.
- Comments are sparse (see Working rules).

## Testing conventions

- Tests mirror the package layout: `tests/test_<subpackage>/test_<module>.py`; the CLI tests in `tests/test_cli/` share fixtures in its `conftest.py` and helpers (`invoke`, `seed`, `write_schema`, …) in `helpers.py`.
- No live Elasticsearch needed for unit tests: `respx` (`respx_mock` fixture) fakes ES, real SQLite files in `tmp_path` back DB tests (in-memory SQLite does not work with async engines; `tests/test_internals` shares the `db_url` fixture in its `conftest.py` and SQLite helpers in `db_helpers.py`), `pyfakefs` (`fs`) for config/schema-file tests that need no DB, `pytest-mock` (`mocker`) only to inject failures, `monkeypatch` for env vars.
- Integration tests live in `tests/integration/` (auto-marked `integration`) and use the real CLI with a real `config.json` via `ESMIGRATE_CONFIG`. The `db_url` fixture parametrizes every test over SQLite, PostgreSQL and MySQL; `es_index` gives a unique index deleted afterwards. `asyncpg`/`asyncmy` are in the dev group so every dev env can reach all backends.
- Async tests are plain `async def` (`asyncio_mode = "auto"`). CLI tests must stay sync `def` because commands call `asyncio.run`; seed/inspect the DB there with `asyncio.run(...)`.
- Fixtures have a docstring (`"""pytest fixture for ..."""`). Parametrized tests often use an indirect `parameter` fixture (`@pytest.mark.parametrize("parameter", [...], indirect=["parameter"])`).
- Docs live in `docs/` as MyST Markdown. `docs/_ext/latest_release.py` renders the Downloads page from the GitHub Releases API at build time (offline local builds get a fallback; CI builds fail without release data); it is tested in `tests/test_docs.py`. The public signing key is published as `docs/_static/zobayer1.asc`. Every ```` ```json ```` block containing `profiles` is loaded by `tests/test_docs.py` (dummy values for `${VAR}`, fake certificate files), so documented config must stay valid; put deliberately invalid examples in ```` ```text ```` blocks. Verify commands and facts against the code before documenting them.
- Every test has a one-line docstring of the form `"""Test fails if ..."""`.
- CLI tests use `click.testing.CliRunner` and a `context` fixture that patches `ContextConfig.load_for` with a profile pointing at a temporary SQLite DB, a temporary `schema_dir` and a fake ES host; they run real commands end to end and assert `result.exit_code` against `Errors.*` plus the stored rows. Their `seed` helper records rows through `start_run`/`finish_run` (`success=None` leaves an interrupted row). Tests that depend on the local time zone use the `local_time_plus_six` fixture from `tests/conftest.py`.
- Git: issue work happens on a `feature/<issue>_<topic>` branch (e.g. `feature/277_history_table`) merged into `main` through a PR with a merge commit; small fixes go to `main` directly when the user asks. A PR takes the main commit's subject as its title and a short summary, `Closes #N` and the Tests/Coverages/Documentations checklist as its body, with the user assigned and the milestone set.

## Modernization decisions

- Plain HTTP to Elasticsearch via **async `httpx`** (no elasticsearch-py); **async SQLAlchemy** for the schema DB. SQLite is built in; PostgreSQL (`elastic-migrate[postgres]`, used by the enterprise deployments) and MySQL/MariaDB (`elastic-migrate[mysql]`) are first-class and must be tested.
- **Python ≥ 3.11 only**; test matrix is exactly 3.11 and 3.14. Code follows 3.11+ idioms: no `# -*- coding: utf-8 -*-` headers, no explicit `(object)` bases, `X | None` and builtin generics in hints.
- **uv** is the project manager (`uv sync`, `uv run`, `uv.lock`), with hatchling + hatch-vcs as build backend (#254).
- Target **Elasticsearch 8**; integration tests run against ES 8 plus PostgreSQL and MySQL in Docker (#259).
- Work is tracked through **GitHub issues** per milestone (`v2.0.0`: modernization, label `modernization`; `v3.0.0`: up/down migrations, tracking issue #275; `gh issue list -m v3.0.0`). Each issue's design is agreed and written into its body before implementation. PRs are restricted to collaborators.
- No automatic dependency updates (pyup removed, no Dependabot).
